# lens 文章写作规范

本规范记录项目的长期写作要求，适用于文章新增、改写、扩充与审阅。技术文章，尤其是 `ai-infra/` 的系列文章，按以下标准组织；思考与系统类文章保留同样的表达与论证要求，采用与主题相称的分析方法。

## 核心标准

### 语言专业，表达准确

- 使用准确、稳定的术语，说明组件职责、因果关系、适用条件和结论边界。
- 用简明中文解释技术问题。专业性来自概念与事实准确，避免用术语密度代替解释。
- 缩写首次出现时给出全称、中文含义及本文语境，例如 MP（multiprocess，多进程）。不同语境下的同名概念应明确区分。
- 区分模型结构、推理引擎、集成接口、传输协议和存储后端，说明它们如何协作。
- 使用有依据的定量描述；性能结论写清比较对象与实验条件，估算写清假设。
- 以完整段落展开观点，每段围绕一个中心，句子之间建立明确关系。删去宣传性措辞、空泛评价、重复概述和对话痕迹。

### 原理深入，解释设计依据

- 从具体问题或约束出发，说明设计如何解决问题，以及为此付出的代价。
- 对关键机制建立“输入 → 处理 → 输出”的完整说明。系统类主题还需交代组件分工、数据位置与执行时序。
- 展开决定正确性和性能的细节，例如前缀依赖、布局匹配、状态转换、同步条件、资源生命周期和关键路径。
- 公式给出符号、维度、单位、假设与关键推导步骤；随后解释公式对应的实际行为。
- 从架构或算法连接到实现。API 名称、配置项与代码片段应帮助理解机制，说明它们何时被调用、影响哪一段流程。
- 分析收益、成本和适用边界。区分数学等价、结构约束、实现行为和实验结论。

### 深入浅出，循序渐进

- 按“具体场景 → 问题 → 必要概念 → 整体设计 → 关键机制 → 分析与验证”的顺序递进。
- 先定义概念，再使用它推导新结论；先呈现整体关系，再进入接口和实现细节。
- 优先用一个贯穿示例连接多个章节，例如两次共享前缀的请求，从匹配、回载一直讲到字节数和成本。
- 抽象机制之后给具体例子，数值例子之后解释它说明了什么，以及哪些条件下结论会变化。
- 图、表、公式和代码各有用途：图解释关系与时序，表辅助比较，公式表达约束，代码对应实现。围绕读者当前的问题使用它们。
- 章节之间说明推理关系，例如“匹配确定哪些状态能复用，下一步需要保证这些状态及时回到正确的 GPU blocks”。

## 篇章布局：技术博客的阅读节奏，论文的论证结构

文章应具备下面这些内容功能，但不要求机械使用“摘要”“引言”“前置知识”等标题。按主题安排自然、具体的章节名，减少重复层级。

| 内容功能 | 需要回答的问题 | 可采用的写法 |
|---|---|---|
| 开篇概述 | 文章讨论什么、核心观点是什么、覆盖到哪里 | 标题下用一至两个自然段概述；系列文章可补一句定位 |
| 问题与背景 | 为什么值得研究，现有方式受什么限制 | 从工作负载、具体场景或已有方法的局限切入 |
| 必要基础 | 读者需要先理解哪些概念 | 只补充后文会使用的知识，提供已有文章链接 |
| 详细原理 | 方案如何工作，为什么正确 | 整体架构、算法推导、数据流、状态与时序，再连接实现 |
| 定量分析 | 收益如何产生，成本如何估算 | 容量、带宽、复杂度或成本模型，注明假设与比较基准 |
| 实践与验证 | 如何复现或检验前面的判断 | 配置、实验步骤、对照组、观测指标和归因方法 |
| 讨论与边界 | 哪些条件下成立，哪些能力另需配置 | 版本限制、负载条件、设计取舍及相关方案比较 |
| 结论与资料 | 读者应带走什么判断，依据来自哪里 | 回答开篇问题，给出适用条件及参考资料 |

其中开篇概述、背景、必要基础和详细原理必须得到实际覆盖。主题不涉及部署时，可用推导、对照案例或公开实验分析承担验证功能；如引用已有基础文章，也需简述本文所依赖的结论。

结构借鉴论文的问题定义、方法分析、证据与局限；表达采用技术博客的自然标题、适中段落和可操作示例。正文说明方案本身的设计价值，避免把文章的整理工作包装成研究贡献。

### 标题与层级

- 每篇文章保留一个一级标题；正文主要使用二级、三级标题。
- 章节名优先描述本节要解释的机制或问题，例如“缓存匹配如何保证复用正确性”“用成本模型判断复用收益”。
- 编号按系列风格选择，避免同时叠加冗长编号与过深层级。
- 将读者需要的细节放到对应机制附近，减少在结尾集中补充基础定义。
- 扩充文章时，重新梳理整体顺序，合并重复段落，让新增内容进入原有论证链。

## 资料、引用与事实核对

- 对版本敏感的行为、配置命令、产品能力、模型支持和性能数据，联网核对官方资料。
- 优先使用原始论文、官方文档、官方仓库及对应版本的源码。重要论断附近放直接支持它的链接，文末保留参考资料。
- 记录资料查阅日期；滚动更新的文档和分支说明其性质。可复现实验尽量记录版本、tag 或 commit。
- 清楚区分论文提出的设计、当前实现的行为、已发布能力及开发分支能力。
- 保留来源的限制条件。一个版本、模型或部署拓扑的结论，不直接推广到所有组合。
- 数据未经实测时明确写成估算、示意或实验方案。引用公开结果时交代来源和关键条件。
- 对关键对象给出完整语义，例如缓存命中要说明命中的是请求、token、chunk 还是字节。

## 公式、代码与实验

### 公式和数值

先定义符号，再给公式与关键推导，最后解释工程含义。计算容量时区分 GB/GiB、MB/MiB；计算性能时区分延迟与吞吐，交代批量、输入输出长度和并行条件。

百分比和倍数写清分母，例如“相对于逐头展开后的缓存布局减少多少”。区分模型整体与每层、单设备与全模型、已命中总量与实际搬运量。

### 代码和配置

- 代码服务于机制解释或复现，并说明运行环境、依赖和版本前提。
- 标注伪代码或省略项；名称、张量形状、配置项和解释保持一致。
- 区分接口约定与特定实现的实际行为，尤其是异步、逐层执行和完成通知。
- 示例使用完整且有效的配置格式，避免混用不同版本或部署模式的参数。
- 正文保留影响理解或复现的实现细节，仓库操作和写作过程放在任务交付说明中。

### 验证与评测

- 实验先明确要检验的判断，再安排对照组与指标。
- 区分功能正确、机制生效与性能有收益。例如文件写入、外部缓存回载和 TTFT 改善，分别需要证据。
- 处理预热、缓存层级、并发、排队与后台任务等可能干扰归因的因素。
- 实测与理论模型不一致时，分析差异；保留未验证事项和不确定性。

## 系列文章与仓库格式

文章位于对应栏目目录，系列采用稳定的文件名与标题格式。沿用现有命名方式，例如：

- `attention-3-mla.md`：注意力机制系列第三篇。
- `kv-cache-offload-1-lmcache.md`：《KVCache卸载》系列第一篇。

frontmatter 使用 `title`、`date`、`description`。日期采用文章实际写作或发布日期，格式为 `YYYY-MM-DD`；不要为了排序随意改动已发布文章日期。描述概括文章对象、主线和读者能获得的理解。

以下是可裁剪的起稿骨架。占位章节名需要按具体主题改写，内容应自然衔接：

```markdown
---
title: 系列名-序号 主题
date: YYYY-MM-DD
description: 文章讨论的问题、机制与分析范围。
---

# 系列名-序号 主题

用一至两个自然段交代具体问题、核心观点、文章范围。

## 从场景说明问题及约束

## 建立后文需要的概念

## 整体架构与组件分工

## 关键机制如何工作

## 用推导或成本模型检验设计

## 实践、实验或对照分析

## 适用条件与设计取舍

## 回答开篇的问题

## 参考资料
```

系列开篇明确范围；后续文章说明与前篇的关系，使用稳定的站内链接。已定义术语保持一致，需要回顾时简述要点并链接相关章节，避免整段重复。

栏目导航与首页近期笔记由项目代码自动扫描文章生成。数学公式使用 `$...$` 和 `$$...$$`。流程图应使用站点已支持的方式；引入新语法或插件前先确认渲染能力。

## 交付前复核

1. 开篇是否明确问题、核心观点与范围，必要基础是否在使用前介绍。
2. 关键原理是否交代依据、处理流程、正确性条件和成本。
3. 专业术语是否准确且前后一致，贯穿示例是否衔接各节。
4. 引用是否直接支持论断，版本行为、估算与实测是否区分。
5. 公式、单位、分母、示例数字和配置格式是否核对。
6. 篇章是否循序渐进，重复内容和无助于理解的细节是否精简。
7. 运行 `npm run build`，检查文章生成、公式渲染、站内链接与导航收录。
8. 按示例内容检查代码语法和计算结果；如未做模型、GPU 或多机实测，在交付时说明实际验证范围。
